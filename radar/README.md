# AI-радар Авито Товаров: еженедельный выпуск от Евы

Каждый понедельник Ева собирает выпуск за прошедшую неделю (со вторника по понедельник, например 17.11-23.11.26), в 21:30 присылает Виктории страницу на просмотр и после ее "ок" отправляет письмо от ее имени. Страница выпуска лежит на `https://nowater.tech/AI-radar/Avito/Goods/<период>`.

Пароль почты и список адресатов хранятся на сервере nowater.tech. Ева их не видит, на другой адрес отправить не может, а адресатам уходит только то письмо, которое Виктория уже получила контрольной копией.

## Порядок в понедельник

1. **19:30.** Ева запускает Шаги 1-4 из инструкции Виктории, каждый шаг - отдельный субагент. Упаковщик сохраняет выпуск в JSON, формат - [example-issue.json](example-issue.json). Текст выпуска он переносит в поля слово в слово и ставит переводы строк так, чтобы первый абзац поля был его сутью: правила ниже.
2. **Сборка.** Сборщик проверяет текст по правилам Виктории и собирает страницу и письмо. Если в тексте есть нарушения, он перечисляет их и ничего не собирает.

   ```bash
   git -C ~/nowater pull --ff-only || git clone --depth 1 https://github.com/vikkyduck/bezvody-frontend ~/nowater
   python3 -I ~/nowater/radar/render.py выпуск.json --out ~/radar/17.11-23.11.26
   ```

3. **21:30.** Ева публикует страницу и отправляет контрольную копию письма на ящик отправителя:

   ```bash
   ssh -F ~/.ssh/nowater-radar.conf nowater-radar publish 17.11-23.11.26 < ~/radar/17.11-23.11.26/page.html
   ssh -F ~/.ssh/nowater-radar.conf nowater-radar test 17.11-23.11.26 < ~/radar/17.11-23.11.26/mail.json
   ```

   Виктории в Telegram уходят файл `page.html`, ссылка на страницу и фраза "контрольная копия письма у тебя в почте".
4. **После "ок" Виктории** - и только после него - письмо уходит адресатам:

   ```bash
   ssh -F ~/.ssh/nowater-radar.conf nowater-radar send 17.11-23.11.26 < ~/radar/17.11-23.11.26/mail.json
   ```

   Если Виктория просит правки, нужно поправить JSON и снова выполнить сборку, publish и test, а потом снова спросить. Если к 23:59 ответа нет, письмо не уходит, а утром Ева напоминает.
5. **После отправки.** Системные сигналы из Шага 2 Ева дописывает в накопительный файл в папке выпусков на Диске.

Что уже сделано по периоду:

```bash
ssh -F ~/.ssh/nowater-radar.conf nowater-radar status 17.11-23.11.26
```

## Согласование через GitHub (без Евы)

Решение Виктории от 24.11.2026: выпуск готовит Claude по расписанию, согласование идет через GitHub, шлюз остается на сервере. Пароль почты и список адресатов по-прежнему знает только сервер.

1. **Понедельник, 19:17 по Москве.** Запланированная сессия Claude проходит шаги "Сканер", "Аналитик", "Редактор", "Проверка фактов" отдельными агентами, собирает выпуск и кладет его в ветку `radar-issue/ПЕРИОД`:

   ```bash
   python3 -I radar/render.py выпуск.json --out radar/issues/17.11-23.11.26
   cp выпуск.json radar/issues/17.11-23.11.26/issue.json
   ```

   В папке выпуска лежат `issue.json`, `page.html`, `mail.json` и `mail-preview.html`. На ветку открывается запрос на слияние.
2. **Сервер раз в 5 минут смотрит в репозиторий** (`deploy/radar_watch.py`). Увидел выпуск в ветке - публикует страницу и отправляет Виктории контрольную копию. Каждая правка в ветке дает новую контрольную копию.
3. **"Ок" Виктории - слияние запроса в main.** Правки - сообщением Claude, он обновляет ветку.
4. **Сервер видит слияние и отправляет письмо адресатам**, один раз.

Что не дает отправить письмо без согласования:

- адресатам уходит только то письмо, которое уже уходило контрольной копией из ветки. Если в main оказалось другое письмо, оно уходит контрольной копией Виктории, а адресатам не уходит. Чтобы его отправить, нужна новая ветка с этим выпуском и новое слияние;
- письмо периода уходит один раз;
- выпуск, у которого неделя закончилась больше 10 дней назад, ничего не запускает;
- наблюдатель не запускает код из репозитория: он читает готовые `page.html` и `mail.json` и передает их шлюзу.

Поставить наблюдателя на сервер (один раз, с Mac Виктории, из ветки main): `deploy/setup-radar-watch.sh`. Остановить: `deploy/setup-radar-watch.sh --off`. Журнал на сервере: `/var/lib/nowater-radar/state/watch.log`.

Репозиторий открытый: текст выпуска виден в ветке до отправки. Страница выпуска тоже открыта по ссылке и закрыта от поисковиков.

## Если выпуск уже написан в документе Word

Когда текст выпуска готов в документе, раскладывать его по полям руками или языковой моделью нельзя: фраза может оказаться пересказанной. Это делает скрипт, слово в слово:

```bash
python3 -I ~/nowater/radar/from_docx.py выпуск.docx --start 2026-11-17 --out выпуск.json
```

- `--start` - первый день недели выпуска, неделя считается как 7 дней.
- Скрипт ждет разделы как в выпуске 6: "Тема письма", "Главный вывод недели", "Главный сигнал недели", "Еще N сигнала недели", сводная таблица, "Что отсеяли как шум". Незнакомый раздел или абзац вне разделов останавливает скрипт с понятной ошибкой.
- В конце скрипт сверяет результат с документом. Если хоть один абзац или ячейка таблицы не перенесены дословно, файл не записывается.
- Карта сути и цифра недели появляются в письме, если в документе есть две строки:
  `Карта сути: Торг / Решение о возврате / Допуск ИИ-агентов / Проверка товара` и
  `Цифра недели: от 4 990 рублей / настройка у avitofoer / пояснение одной фразой`.
  Без них письмо соберется без карты и цифры. Слова для этих строк скрипт сам не выбирает.
- Сокращать текст для письма не нужно: в письмо идет первый абзац каждого поля, а из абзаца длиннее 260 знаков - первая фраза.

## Три уровня чтения

Выпуск построен по пирамиде Минто. У читателя три уровня, и у каждого свое место:

1. **Суть** - одна фраза о том, что изменилось за неделю. Она открывает письмо и страницу. Раздел называется "Суть", не "Вывод".
2. **Опоры** - сигналы с заголовками-выводами: что произошло, что это может значить для выручки, возможный вопрос клиенту. Это письмо.
3. **Проверка** - источники, полный текст, идеи фич, сводная таблица, шум, оговорки. Это страница на сайте. Нужна обязательно, но в письме она шум.

Слова "вывод", "аргументы", "история" в подписях не пишутся: это названия уровней для автора, а не для читателя.

## Что идет на страницу

Весь выпуск слово в слово. Сборщик не сокращает, не переставляет и не пересказывает текст. Упаковщик кладет выпуск в поля JSON дословно, как в [example-issue.json](example-issue.json):

- Каждое предложение выпуска попадает в одно из полей целиком. Сокращать, объединять и переименовывать разделы нельзя.
- Ссылка на источник остается там, где стоит в тексте: `[подпись](https://адрес)`. Скобки и пробелы в адресе кодируются (`%28`, `%29`, `%20`). Отдельный список `sources` нужен, только если в тексте сигнала ссылок нет. У каждого сигнала должна быть хотя бы одна ссылка: в тексте или в списке.
- Заголовок блока в поле не входит. "Что происходит.", "Почему это важно для выручки.", "Возможные фичи для продукта.", "Возможный вопрос клиенту:" - это подписи, их ставит сборщик. Если в выпуске заголовок звучит иначе, его передают в `labels`, список ключей - `LABELS` в [render.py](render.py).
- `main_signal.title` - слова после "Главный сигнал недели:" с прописной буквы. У сигнала `title` - первое предложение абзаца без точки, `text` - весь остальной абзац.
- `badge` - необязательная метка сигнала: слова из скобок в первой колонке сводной таблицы, дословно. Например "eBay, один вторичный источник".
- `name` и `number` - название и номер из первой строки выпуска: "Слабые сигналы селлеров. Выпуск 6".
- `noise` - каждый пункт одной строкой, как в выпуске.

Это правило закреплено тестом `test_page_carries_the_issue_word_for_word`.

## Что идет в письмо

Читатель письма - продажи. Письмо короткое, около двух минут. Оно берет из каждого поля **первый абзац** и убирает из него ссылки на источники. Своих слов в текст выпуска сборщик не добавляет (тест `test_letter_takes_its_words_from_the_issue`). Упаковщик решает одно: где в поле поставить перевод строки.

- `summary`: первый абзац - суть недели одной фразой. Остальное читается на странице.
- `main_signal.what`: первый абзац - что произошло, одна-две фразы. `main_signal.why`: первый абзац - кого это касается.
- `signals[].text`: первый абзац - одна фраза о том, что произошло.
- Если абзац длиннее 260 знаков и не разбит, в письмо идет только его первая фраза.
- `short` у главного сигнала и у каждого сигнала - два-три слова для карты сути. Слова берутся из сути, в именительном падеже: "Торг", "Решение о возврате". Карта есть, только если слова даны у всех сигналов.
- `figure` - цифра недели: `value` - число словами выпуска ("от 4 990 рублей"), `caption` - короткая подпись к нему словами выпуска ("настройка у avitofoer"), `note` - необязательная фраза выпуска о том, что это значит. Без поля блока нет.
- Строки `table` идут в том же порядке, что и сигналы: первая - главный сигнал. Из строки в письмо попадает возможный вопрос клиенту этого сигнала.
- Идеи фич в письмо не идут: они для Продукта и читаются на странице, в тексте сигнала и в сводной таблице.
- В первом абзаце лучше обходиться без двоеточий и скобок: в письме они смотрятся как знаки из файла.

## Как выглядит письмо

1. шапка: NOWATER.TECH, название издания, строка из трех сведений - номер выпуска, даты, время чтения
2. суть недели: одна фраза, самая крупная в письме
3. карта сути: по плитке на сигнал, по две в ряд
4. главный сигнал: заголовок-вывод, что произошло, почему это важно для выручки, цифра недели на розовой заливке, возможный вопрос клиенту отдельным блоком
5. остальные сигналы: заголовок-вывод, одна фраза, возможный вопрос клиенту
6. одна кнопка "Весь выпуск на сайте" и подпись

Правила оформления, утвержденные Викторией 24.11.2026:

- **Три цвета текста:** светлый, розовый и темный на розовой заливке. Серого текста нет: в почте он читается тяжело.
- **Пять размеров шрифта:** 13, 17, 20, 26 и 36 px. Manrope в почте не загружается, иерархию держат размер и жирность.
- **Подпись блока стоит на своей строке, текст начинается с новой.** Подпись набрана обычными буквами, жирно.
- **Знаки из файла заменяет верстка.** Двоеточий после подписей нет. Вопрос клиенту идет без кавычек. Суть и заголовки идут без точки. Слова в кавычках внутри фразы выделены жирностью.
- **Строки не рвутся некрасиво.** Сборщик сам ставит неразрывные пробелы: предлог и союз остаются со следующим словом, число - со словом после него, разряды числа - вместе, слово с дефисом не переносится. Два последних слова заголовка и абзаца стоят вместе, если пара не длиннее 16 знаков. Слова выпуска при этом не меняются. В текстовой версии письма неразрывных пробелов нет.
- **Все края на одной линии.** Номер выпуска стоит по левому краю, время чтения - по правому, даты - между ними с равными промежутками. Ряд карты сути - одна плашка с двумя колонками одной высоты.
- **Отступы кратны восьми:** подпись и текст - 8 px, блоки внутри сигнала - 24 px, сигналы - 48 px, разделы - 56 px.
- **Одна ссылка** - кнопка на страницу выпуска. Навигации, счетчиков, меток, пояснений под кнопкой и адреса текстом в письме нет.
- **Свои слова сборщика** - знак, время чтения, подпись на кнопке и подпись автора. Команд читателю нет: тон письма вежливый и деликатный.

Время чтения сборщик считает сам по словам письма.

- Письмо собрано для почтовых программ: таблицы, стили на самих элементах, без картинок. Шрифт Manrope в почте обычно не загружается, тогда текст набран системным шрифтом устройства.
- Строка превью в списке писем берется из необязательного поля `preheader`. Если поля нет, это суть недели. Невидимых символов после строки превью сборщик не ставит: проверочное письмо с таким хвостом 24.11.2026 не дошло до ящика на Яндексе, то же письмо без него дошло. Причина не доказана.
- Письмо перед отправкой можно открыть в браузере: `mail-preview.html`. Как оно выглядит в Outlook, Почте Apple, Яндекс Почте и Mail.ru, видно только в самих ящиках: контрольная копия для этого и нужна.
- Страница выпуска публикуется раньше письма: шлюз не отправит ни контрольную копию, ни письмо, пока страницы периода нет на сайте.

## Чего шлюз не делает

- Не отправляет письмо второй раз и не меняет страницу после отправки.
- Не отправляет письмо, которое отличается от контрольной копии хотя бы одним знаком.
- Не повторяет отправку, если она прервалась и неизвестно, ушло ли письмо. Тогда нужно открыть ящик отправителя. Если письма там нет, отметку снимает root на сервере nowater.tech: `rm /var/lib/nowater-radar/state/<период>.sending`.

## Настройка и изменения

Шлюз ставится один раз с Mac из ветки main: `deploy/setup-radar.sh`. Сменить ящик, пароль или адресатов - запустить его еще раз. Пустой пароль оставляет прежнюю почту, пустой список - прежних адресатов.

Отправитель по решению Виктории от 24.11.2026 - `vu@withoutwater.ru`. Адрес в коде не записан: его задает `deploy/setup-radar.sh`. Какой ящик стоит на сервере сейчас, видно в ответе команды `test`: "контрольная копия отправлена на <адрес>". Если там другой адрес, нужно запустить `deploy/setup-radar.sh` и ввести сервер почты этого ящика, сам адрес и пароль приложения.

Журнал шлюза: `/var/lib/nowater-radar/state/log` на сервере nowater.tech.

Тесты: `python3 -m unittest discover -s tests -p 'test_*.py'`.
